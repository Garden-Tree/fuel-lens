# 技術スタックと選定理由

本ドキュメントでは、FuelLensプロジェクトにおいて採用した主要な技術・フレームワークと、それらを選定した背景・理由について解説します。

## フロントエンド・フルスタックフレームワーク

### Next.js (App Router) / React
- **選定理由**: Reactのエコシステムをフル活用しつつ、ルーティング管理、サーバーサイド処理（API Routes）、レンダリングの最適化を一つのフレームワークで完結させるため。App Routerによる直感的なディレクトリ構造と、Server Componentsによるパフォーマンス向上も目的としています。

### Tailwind CSS (v4)
- **選定理由**: ユーティリティファーストな設計により、CSSファイルを行ったり来たりすることなく、コンポーネントと同等のスピードでスタイリングを行えるため。また、最新のv4ではさらに軽量かつ高速化されているため採用しました。

## 認証とデータベース

### Clerk (@clerk/nextjs)
- **選定理由**: 認証（Authentication）とユーザー管理を迅速かつ安全に実装するため。Next.jsとの親和性が非常に高く、コンポーネント（`<SignedIn>`, `<SignInButton>` など）を配置するだけで高度なログイン体験を提供できるため、開発のスタートダッシュに最適です。

### Supabase (@supabase/supabase-js)
- **選定理由**: バックエンド・データベース（PostgreSQLベース）として採用。BaaS（Backend as a Service）としてRDBの高い表現力を持ちながらも、REST APIを介したフロントエンドからの直接データ操作が容易だからです。また、ClerkとのJWT連携（カスタムクレームを活用したRLSの実装）の相性が良いため、セキュアな構成を構築しやすい点も評価しました。連携の仕組みは [architecture.md](./architecture.md#7-認証) を参照してください。

## AI / 画像処理

### Google Gemini API (@google/genai)
- **選定理由**: レシートの文字読み取りやメーターの数値抽出（OCR並びに意味理解用途）として、強力なマルチモーダル処理能力を持つGeminiを採用。複雑なレイアウトのレシートからも「給油量」「合計金額」などを文脈ベースで高精度に取得できるため利用しています。

### browser-image-compression
- **選定理由**: ユーザーがスマートフォン等のカメラで撮影した解像度の高い画像を、解析用のバックエンドAPIに送信する際、通信量やAPI側のペイロード上限（制限）を回避するため。クライアントサイドで素早く圧縮処理を行い、UXの低下を防ぎます。

## UI / その他ライブラリ

### lucide-react
- **選定理由**: クリーンで一貫性のあるデザインのSVGアイコンセット。軽量であり、Tailwind CSSとの親和性も高い点から採用しました。

### recharts
- **選定理由**: 給油履歴や燃費の遷移をグラフ化するため。React向けに作られており、コンポーネントベースで柔軟なチャートを直感的に組むことができるため採用しています。

## 運用 / インフラ

### Vercel Cron + GitHub Actions (Supabase keepalive)
- **選定理由**: Supabase Free プランは約 7 日間アクセスが無いとプロジェクトが一時停止されるため、定期的に DB へ軽い書き込みを行う必要があります。Vercel Cron を主経路、GitHub Actions を予備経路として二重化しました。構成と設定手順は [operations.md](./operations.md#3-supabase-の自動停止と-keepalive) を参照してください。

### SQL マイグレーション (schema-as-code)
- **選定理由**: Dashboard 上で手作業したスキーマ・RLS ポリシーはプロジェクトを作り直すと失われるため、`supabase/migrations/*.sql` として冪等な SQL をリポジトリに保持しています。適用手順は [supabase/README.md](../supabase/README.md) を参照してください。
